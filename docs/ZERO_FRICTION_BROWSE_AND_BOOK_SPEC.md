## 1. Journey as-is: every stop the user hits today

Message: *"go to marriott.com and book me a hotel in Chicago this weekend"*, model=Auto, Act mode.

1. **Routing works.** `sendMessage` → `buildChatAutomationPlan` (ChatTab.tsx:6983) → local-intent split fails closed (localComputerAwarenessIntent.ts:4645-4647; `OPEN_URL_RE` is $-anchored at :315-316) → `buildChatComputerRequestRoute` fires (chatAutomationPlanner.ts:917) → browser route, confidence 0.96.

Note: `alwaysConfirmFloor=[]` — "book" is NOT a pay-floor verb (`FLOOR_CATEGORY_VERBS.pay` = pay|purchase|buy|checkout|charge, :617-633), so the floor does not fire; the generic side-effect gate does. Autonomy maps this to `userEffort='approve'` (chatComputerTaskAutonomy.ts:130-136) and the "Approve browser run / Ready for review" notice (chatComputerRequestUx.ts:162, :349).
3. **STOP 2 — structural preview tap.** `executeSharedComputerTask` (ChatTab.tsx:2267) → entrypoint `browser_runtime` (computerTaskExecution.ts:155) → the `run_computer_task` handler only calls `describeComputerUsePlan` (ChatTab.tsx:2818-2822), which hardcodes `requiresApproval: true` (computerUse.ts:1175). The dispatch here passes no `approvalGate` (ChatTab.tsx:2806-2817), so `chatApprovalGate`/`chatAutoApproveSettings` (`browser_click:'ask'`, chatAutoApproveSettings.ts:43,:74) are dead weight on this path.
4. **Parallel-answer bug.** Because `shared.browser===true`, sendMessage falls through (ChatTab.tsx:6999-7002) and SwanBot streams a plain-text hotel answer on top of the plan card.
5. **Tap Allow.** The dialog's `onAllow` is the sole `computerUseTask.run` call site (ChatTab.tsx:11267) — no `sessionId`, no cost overrides. If Browserbase creds are absent or cost-preference picks local, the legacy `executePlan` path halts at *every* navigate/fill (computerUse.ts:256, :268-273, :1023-1044).
6. **Run executes on defaults that kill a 20-40-step booking flow:** 12 iterations / hard cap 20 (index.ts:417), 75k tokens (:418), **$0.75 cost cap** (:434 — client body omits `maxCostUsd` entirely, computerUseAgent.ts:139-148), 5-min wall clock (:480). 7. **STOPS 3..N — prompt over-asking.** The SAFETY block demands `ask_user` before ANY Confirm/Submit/Send button AND before entering personal info (index.ts:911-917), so a booking flow pauses at guest details, intermediate confirms, and payment — not once.
8. **Options arrive dead.** `<FINDINGS>` are parsed only at terminal end_turn (index.ts:675, extractStructuredFindings :1275) and posted to chat as a flat markdown numbered list (ChatTab.tsx:5414-5430), metadata `{runId}` only. Structured card rendering exists only in the transient ComputerUseLiveCard overlay. The run is over; the Browserbase session is abandoned.
9. **STOP — "book option 2" is a dead end.** Verified: the route returns null (`explicitComputerSurfaceRequested`, chatComputerRequestRouter.ts:800, :1458) and the message falls to plain SwanBot chat. Even when phrased to re-route, it repeats stops 2-3 with a **fresh** session, saved only by the edge's 30-min textual followUpContext (index.ts:366-396).
10. **Mid-run confirm exists but is fragile:** `ask_user` → `confirmation_required` SSE + DB poll (index.ts:766-768, askUserAndWait :995-1002), rendered only in the overlay (ChatTab.tsx:11360-11378); 120s timeout auto-answers No.

## 4. Follow-up-booking design ("book option 2")

**State:** WI-4/WI-5 keep a per-thread `lastComputerRun {runId, sessionId, findings, completedAt}` — already persisted via computerTaskState at completion (ChatTab.tsx:~5378-5395); read it back on thread load. Pass `(circleId, userId, threadId)` into `useComputerUseTask` (currently circleId-only, so durable pending-question records are write-only).

**Intercept:** at the top of `sendMessage`, **after** the `pendingClarificationRef` check (collision guard — "option 2" could match an open clarification's chips), before `buildChatAutomationPlan`:

- **Case A — run alive, pendingConfirmation open** (agent asked "Which option should I book?" via confirmation_required whose options are the findings): map the typed reply/ordinal to an option and call `resolveComputerUseConfirmation(id, choice)` (computerUseConfirmations.ts:11). The edge's 500ms poll resumes the same loop; no new route, no dialog. This is the "run stays alive" path and requires WI-3's longer confirm window.
- **Case B — run terminal, findings persisted:** synthesize `"Book: <title> — <url> (continuing run <id>)"` and call `computerUseTask.run(task, { sessionId: lastRun.sessionId })` directly. Plumbing is fully built and unused: hook option (useComputerUseTask.ts:160) → body `sessionId` (computerUseAgent.ts:144) → edge session reuse (index.ts:523-525). Add `keepAlive`/timeout to `openBrowserbaseSession` (index.ts:1359 — currently sends only projectId/region) so the session survives between legs.
- **Case C — session expired:** fall back to a fresh session; the finding URL in the task plus the edge's automatic 30-min followUpContext (index.ts:366-396, built for "the cheapest one") makes re-navigation one hop.

Card "Book" taps and quickReply chips feed the same interceptor via `sendMessage(text)`.

**Where the single confirmation surfaces:** the booking leg proceeds ask-free through room selection and guest details (WI-3), then emits exactly one `confirmation_required` at the final payment/booking submit with amount+merchant+live price. Mirror it as a **persisted chat bubble** with Yes/No actions wired to `resolveComputerUseConfirmation` (today it exists only in the overlay, ChatTab.tsx:11360-11378), idempotency-keyed. Timeout ≥300s; on timeout, paused-resumable partial_result with sessionId → a "Confirm & resume" chat action. Payment-card entry (no vault support exists) uses the existing `human_takeover` flow — user types the card in the live session view, isolated from model context — then the single confirm fires at submit.
